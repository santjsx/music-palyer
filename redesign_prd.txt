Product Requirements Document — TuneHive Visual Redesign

Product: iPod Modern → next-generation neon/ambient music player UI
Repository: santjsx/music-palyer
Platform: Android
UI: Kotlin + Jetpack Compose
Status: Redesign specification
Primary objective: Replace the existing skeuomorphic/iPod visual language with a premium, dark ambient music-player experience inspired by the supplied reference—while preserving the existing audio engine, data, playback capabilities, and advanced functionality.

1. Executive Summary

The current application has substantial technical depth: native audio infrastructure, Room, Compose UI, Cover Flow, lyrics, equalization, Wi-Fi synchronization and other functionality. The problem is not lack of features.

The problem is product presentation.

The existing product positions itself visually as an iPod/hardware-skeuomorphic player. The new direction should position it as a premium modern music application built around:

Darkness + album art + ambient light + neon green + tactile controls.

The supplied reference establishes the visual direction, but it should not be copied literally. The goal is to extract its design principles and build a coherent production-grade design system around them.

The redesign must feel:

premium
immersive
minimal
modern
tactile
responsive
visually consistent
unmistakably music-first

It must not feel like:

a generic Material 3 template
Spotify imitation
an iPod skin
a collection of unrelated screens
a UI covered in unnecessary neon effects
2. Product Vision
Vision

Create an Android music player where the music and its artwork become the visual identity of the interface.

The application should feel almost like a physical listening environment:

Album artwork
      ↓
Ambient color extraction
      ↓
Background atmosphere
      ↓
Neon accent
      ↓
Interactive controls
      ↓
Motion
      ↓
Immersive listening experience

The UI should disappear into the listening experience rather than compete with it.

3. Design North Star

Every screen must satisfy five principles.

3.1 Music-first

Artwork and playback state receive the strongest visual hierarchy.

3.2 Ambient

Album artwork influences the surrounding environment through blur, gradients and subtle color illumination.

3.3 Tactile

Buttons should visually communicate:

what is interactive
what is currently active
what just happened
3.4 Restrained

Neon is an accent, not the entire UI.

Bad:

Everything glows green.

Correct:

Green appears where attention or interaction is required.

3.5 Systematic

Every component must originate from the same design system.

No screen should introduce arbitrary:

corner radii
colors
shadows
font sizes
icon sizes
spacing
animation durations

32. Motion Design System

Animation must communicate state, not merely decorate the UI.

Durations

Suggested semantic tokens:

Micro       ~100ms
Fast        ~160ms
Standard    ~250ms
Emphasis    ~350ms
Ambient     ~600–1000ms

Don't animate everything.

Required animations
Play button
play → pause

Use morph/crossfade.

Artwork

Very subtle scale/opacity changes during playback.

Navigation

Shared-axis or fade/slide transitions.

Mini-player

Animate from bottom surface into full player.

Category selection

Subtle pill movement/color transition.

Progress

Smoothly interpolate playback position.

33. Haptics

Existing haptic infrastructure should be retained where useful.

Use haptics for:

play/pause
scrub interactions
toggles
meaningful confirmations

Do not vibrate for every tap.

Haptics should reinforce physicality.

34. Accessibility Requirements

This is non-negotiable.

Minimum requirements
Touch targets should meet Android accessibility expectations.
Screen reader labels for icon-only controls.
Content descriptions for artwork where meaningful.
Dynamic font scaling.
Contrast validation.
Do not communicate state using color alone.
Playback state must be exposed semantically.
Seek functionality must remain accessible without circular gestures.

The neon aesthetic cannot override accessibility.

35. Adaptive Layout

Do not design only for one phone resolution.

Compose is explicitly designed to support adaptive layouts across different window sizes, orientations and form factors. Android recommends window size classes and Material 3 Adaptive for this purpose.

Compact

Bottom navigation:

Home | Search | Library | Settings
Medium

Navigation rail + content.

Expanded

Potential:

Navigation rail
      │
      ├── Library/list
      │
      └── Detail/player
Tablet

Now Playing could become:

┌──────────────┬────────────────────────────┐
│ queue        │                            │
│              │       album artwork        │
│              │                            │
│              │       controls             │
└──────────────┴────────────────────────────┘

This is preferable to stretching a phone layout across a tablet. Android's current adaptive guidance explicitly favors window-size-aware layouts rather than simply scaling a compact UI.

36. Performance Requirements

The redesign must not turn the player into a GPU-heavy visual demo.

Requirements
Smooth scrolling.
No unnecessary recompositions.
Artwork caching.
Avoid repeated bitmap processing.
Avoid continuous expensive blur operations.
Ambient background updates only when artwork changes.
Animations should be suspendable when app is backgrounded.
No unnecessary allocations during playback.
Circular progress must remain smooth during active playback.
Target
60 FPS baseline
90/120 FPS where supported

The UI must remain responsive while the native audio engine is operating.

37. Audio Architecture Boundary

The redesign must not couple UI components directly to low-level audio implementation.

Conceptually:

                 UI
                  │
             UI State
                  │
             ViewModel
                  │
          Playback abstraction
                  │
          ┌───────┴────────┐
          │                │
       Media3          Native Audio

If Media3 is used for a given playback path, its Player abstraction already exposes standard operations such as play, pause, seek and track information.

The UI should not care which underlying playback implementation provides those operations.
